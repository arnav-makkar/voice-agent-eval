00 · What the evidence actually says

Two P0s collapse into one root cause and one blind spot

All of this comes from artifacts already on disk. No new runs, no new model calls. I reconciled the append-only inbound journal against the pilot's own timestamps.

ROOT CAUSE · INFRASTRUCTURE

The tool path was dead for the entire v19 pilot window

The append-only journal at artifacts/tool_service/inbound_requests.jsonl holds 46 requests. Sarvam's documented tool-caller IP 4.213.167.70 appears 12 times — real platform-originated calls, with 401s failing closed, 200s succeeding, and genuine state mutation. That path demonstrably worked.

Then it stopped. The last platform-originated tool call was 09:46:25Z. The last inbound request of any kind was 10:04:09Z, from localhost. The v19 pilot ran 10:38:32Z → 10:46:12Z.

requests from 4.213.167.70 first 08:24:17Z last 09:46:25Z requests from tunnel origin first 08:19:28Z last 09:58:18Z last inbound request, any origin 10:04:09Z v19 pilot window 10:38:32Z → 10:46:12Z inbound requests during that window 0 — not one. not even a 401.

The tunnel was a free pinggy session with a 60-minute TTL, opened around 08:19Z. By 10:38Z it had been dead for roughly 40 minutes, and the Indus tool config still pointed at its hostname. Every tool invocation would have failed at the network layer, before ever reaching your service — which is exactly why the journal is silent rather than full of errors.

Consequence: the post-flight recorded required_tool_missing as a P0 agent defect. It is very likely an environment defect. The framework has an “infrastructure-invalid vs agent-failure” concept, but it only covers provider failures — not tool-transport failures. So a dead tunnel was scored as a badly behaved agent.

BLIND SPOT · MEASUREMENT

The harness cannot see a tool call it does not receive

Across every pilot ever run — v16, v18, v19, nine records total — num_tool_calls is 0 and tools_called is empty, in all of them. And samvaad_events.jsonl contains zero tool-related events in all eight streams.

grep -c tool samvaad_events.jsonl → 0 (v16 ×2, v18 ×3, v19 ×3) num_tool_calls across 9 records → 0, tools_called: [] therefore "0 tool calls" is inferred from our own state, never observed from the platform.

That single number is currently doing three incompatible jobs. It cannot distinguish (a) the agent never decided to call the tool, from (b) the agent called and the request died in transit, from (c) the call succeeded but state did not update. The v19 HOLD was issued without knowing which of the three happened.

This is the finding worth presenting. A grading system that cannot separate “the agent misbehaved” from “my plumbing was down” is not yet trustworthy. Finding that in your own harness, naming it, and closing it is the self-improvement loop — applied one level up, to the evaluator instead of the agent.

HONEST CAVEAT

The evidence does not prove the agent is innocent

Hypothesis (b) is the most likely reading, but it is not proven. It remains entirely possible the agent never attempted a call, and the dead tunnel is a coincidence. Do not write the exoneration into the deck before the experiment runs. P1 and P4 exist precisely to separate the two, and they cost nothing.

The second P0 — terminal_claim_without_tool_evidence, the agent saying “मैंने callback schedule कर दिया है” with no state write — stands regardless. Whether the tool was unreachable or never called, the agent asserted a completed side effect it had no confirmation of. That is a genuine, serious, product-owned defect, and P3 fixes it.

What “a loop I can showcase” actually requires

The reason this feels unfinished is that the loop was never given an acceptance test. Here is one. A demonstrable loop needs five things, on the same axis, with the same denominator.

The reframe that makes this winnable. You have been treating EVA-X as the “after” metric. It is the wrong one to lead with — it is a soft experience score, judge-mediated, and it is the hardest thing to move in three calls. The metric that is hard, live, voice-only, currently zero, and directly fixable is execution truth: does the agent's terminal claim have a matching tool result behind it?

Before: 0 of 3 calls produced a tool effect; 2 of 3 asserted a completed action anyway. After a working transport and a claim lock, the honest target is 3 of 3 grounded. That is a real, voice-layer, production-relevant improvement with a hard denominator, and it is not a text result being dressed up as a voice result.

02 · The core idea

Three rungs, not one leap — so each repair gets its own credit

The temptation is to fix everything and run one “after”. Don't. That bundles an infrastructure fix with a prompt change and gives you a confounded result any competent interviewer will take apart. Separate them. It costs three extra calls and buys clean attribution.

Rung 1 · have itv19 · dead path

The before, already on disk

Three Hinglish calls, 2 evaluator-valid, 0 task passes, 0 tool events, 1 timeout. EVA-A 0.417 / EVA-X 0.461. Cost: already spent. No re-run needed — this is your baseline arm.

Rung 2 · 3 callsv19 · live path

Same prompt, working transport — the diagnostic that settles it

Identical agent version, identical frozen records, only the tool route repaired. This isolates the environment fix and answers the (a)-vs-(b) question directly: if tool events now appear, the agent was always trying and the harness was blind. If they still don't, the defect is genuinely in the agent and P3 is where the work is.

Rung 3 · 3 callsv20 · claim lock

The prompt/workflow repair, measured on its own

Adds the terminal-claim lock and the opening-once rule on top of a known-good transport. Any delta from rung 2 is attributable to the repair, not the plumbing. This is the “after” you present.

Why this is the strongest version of your story. A three-rung ladder shows something a single before/after cannot: that you can attribute a change to a cause. Rung 2 is a control. Most candidates never build one. And if rung 2 already fixes execution truth, you have discovered — with evidence — that your headline P0 was an artifact of your own test rig, which is a better finding than a green number.
