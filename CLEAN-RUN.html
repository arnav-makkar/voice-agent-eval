One methodological flag, stated now rather than found later. Building the 170 after seeing BASE fail could inflate the before/after gap — a suite written to catch known failures is easier to improve on. Two mitigations, both binding: the families come from the domain taxonomy (the same 14 used all along) rather than from specific observed failures, and the manifest records which families were pre-specified versus discovered in steps 2–3. The 86 blind scenarios and the sealed 12 are authored before any candidate exists, so the headline number is never tuned.

Validity (a session counts only if evaluator-valid and transport-healthy), decision rules (text = blind-split paired win, zero severe regressions; voice = grounded-claim rate and required-effect completion; human tier = descriptive, n too small to gate), the synthetic-data rule (generated scenarios enter the development split only, tagged synthetic), and the budget ceiling. One JSON every later artifact references.

Step 4 · ~4 h · metered Sarvam text API

170 synthetic conversations, then the text baseline

4

Build, freeze, measure

the tier that gives the optimiser something to learn from
01
Generate 170

14 families × 4 languages × 3 variants, plus two language-switch scenarios. Splits 84 development / 43 validation / 43 regression. Every scenario requires an explicit record_disposition with the exact outcome; ~60 additionally require a business write with exact arguments. Every scenario's rubric carries the full tool catalogue — unused tools stay listed, per your rule.

02
Why all-tools is strict, not cosmetic

When an agent merely declares an outcome without calling the tool, the runner writes that state itself and the write never enters the tool log. So state passes while the required-action check fails. Say-versus-do becomes the pass condition on all 170.

03
Freeze, then measure BASE on all 170

Suite hashed before any candidate exists. Validation and regression are never shown to any optimiser. Full panel: task success, five accuracy components, tool execution, experience, first-break owners — sliced by language, family and persona. First five episodes price the Sarvam API before the rest run.

AcceptanceFrozen 170 + BASE text baseline. Combined with steps 2–3: 200 conversations measured on BASE.
Step 5 · ~4 h · free

5

Diagnose → three arms → blind gate → commit v2

01
Diagnose all three tiers into one taxonomy

Every failure becomes a packet: verbatim evidence turn, first breaking turn, owning component, severity. Text, human and voice failures rank together. This is a deliverable in itself — the ranked failure taxonomy is what a real engagement produces in month one.

02
GEPA, properly resourced this time

~200 metric calls against the 84 development scenarios (the last campaign gave it 48), Pro-model reflection over real failure packets, multiple proposals, full MLflow lineage under campaign-2.

03
Two competing arms

Manual repair from the same packets. And a no-diagnosis control — same model, same budget, raw failing transcripts, no routing. That control is the bar the framework must beat: it answers “would one call to a good model have done this anyway?” If the control wins, I report that.

04
The gate picks, blind, then you commit

Candidates scored on the 86 optimizer-blind scenarios, per case, no severe regression averaged away. Sealed 12 opened once for the winner. Losers preserved in MLflow. Then the exact gated prompt goes into Indus as v2, rollback target v1.
