Executive evidence brief · 21 August 2026

The text repair worked. The voice candidate did not.

Loopline is a governed evaluation, diagnosis, improvement and release system around a deployed Sarvam Indus agent. It shows the full loop—original, evaluation, repair, unchanged re-evaluation and decision—without turning a failed live pilot into a success claim.

Objective assessment

Lead-PM strength, with named evidence gaps.

Product architecture · A

Evaluation, improvement and release are separate products. The optimiser cannot grade or approve itself.

Execution truth · A

Disposition, required actions, tool arguments, state diffs and guardrails are executable. The authenticated backend control passed all nine checks.

Experiment discipline · A−

Manual and GEPA arms competed; a 28/30 optimiser result was rejected for severe per-case regressions. Failed candidates and the failed v19 pilot remain visible.

Governance · A

Frozen datasets and evaluators, per-case anti-regression rules, human approval, rollback and machine-readable PASS/HOLD decisions.

Demo product · A−

Light/dark product console, eight deep cases, audio evidence, tools, state deltas, evaluator accountability and release center.

Not A yet
Live voice evidence · C / HOLD

Latest result: 0/2 valid task passes, zero tool events, one timeout. This is a failed candidate, not improvement evidence.

Workflow enforcement

Prompt prose did not prevent repeated openings, unsupported terminal claims or a non-Hinglish script switch. These need explicit runtime state and verifier blocks.

Independent judging

Judge-vs-executable κ is published: 0.46 for failure detection and −0.13 for component ownership. An independent second LLM judge family and judge-vs-judge κ are still open.

Optimizer breadth

GEPA and manual repair are real. MIPROv2 has not been run and must not be advertised as an executed arm.

Business outcome

The measured proxy is explicit commitment. Settled cash, roll rate and complaints require a ledger/outcome join that is designed but not measured.

The product

Three responsibilities. One closed loop.

01

Evaluation engine

  • Versioned hidden-goal scenarios
  • Realtime or stateful execution
  • Validity before scoring
  • Deterministic truth before judges
  • First break and owning component
02

Improvement engine

  • Routes prompt, extractor, tool, workflow, runtime or policy failures
  • Manual and optimiser arms
  • Versioned hypotheses and diffs
  • L0–L3 implemented; L4 argued; L5 deliberately refused
  • Negative candidates retained
03

Release controller

  • Exact paired per-case comparison
  • No severe regression can be averaged away
  • Fresh final opened once
  • Pilot before paid matched suite
  • Promote, hold or rollback—with a human

Interview pitch

Path to a defensible live “after”

Fix the path before buying another score.

The interview product is presentation-ready as a governed system with a truthful HOLD. A live improvement claim still requires the gates below.

Prove platform-originated tool invocation locally

One Indus call must appear in the append-only journal with correct run ID, account ID, auth, arguments and state delta. Direct endpoint success is necessary but not sufficient.

Move terminal discipline into workflow state

Opening can execute once; success language is unreachable until the matching tool returns success; timeout and tool error have explicit truthful fallbacks.

Use the corrected frozen pilot

The next three records are normal Hinglish only. Dates are rebased and a deterministic post-flight rejects wrong script, stale dates, missing tools and unsupported terminal claims.

Ask for authorization, then run exactly three

Advance only at 3/3 evaluator-valid, 3/3 required task effects, zero severe integrity failures and an acceptable transport/experience floor.

Only then run the frozen 18×2 match

Same 18 records on baseline and candidate. Publish EVA-A, EVA-X, task effects, pass rates, confidence intervals, invalid-call rate and a signed promote/hold/rollback decision.

Close the remaining credibility gaps

Add an independent second judge and judge-vs-judge κ; run MIPROv2 only if it answers a real optimizer question; join commitments to settled payment, complaints and roll-rate guardrails.
