Objective audit · 19 August 2026

From prompt experiment to evidence-backed voice improvement system.

The framework direction is strong. The current evidence is not yet strong enough to claim that the deployed voice agent improved. This plan closes that gap without pretending the existing synthetic cases are real calls.

Unbiased conclusion

Keep the architecture. Do not deploy the current GEPA finalist yet.

The project already demonstrates trace ingestion, failure-derived evaluation, component routing, prompt search, experiment lineage, and release gating. Its main weakness is evidence quality: most candidate scoring is a single next-response text test, evaluator attribution is weak, no candidate voice benchmark exists, and no executable EMI backend verifies tool side effects.

The 200 items are generated evaluation cases—not 200 calls. Of those, 170 pre-held-out cases were scored. Thirty remain sealed. The only real voice corpus is the initial 20 V12 calls.

01 · What exists now

Substantial work is complete. Its boundaries must stay explicit.

The current system is more than a GEPA wrapper. It is a governed offline learning loop. But several layers are still provisional or simulated.

Strong and usable

Framework infrastructure

  • Exact Sarvam Instant Outbound integration with dry-run safety.
  • Canonical trace schema, artifact hashes, run IDs and redaction.
  • Frozen 20-call baseline membership.
  • Failure mining and first-breaking-event diagnosis.
  • Typed repair routing: prompt, extractor, workflow, tool, model and human review.
  • MLflow experiment logging and Loopline monitoring dashboard.

Strong but provisional

Evaluation and experiments

  • 200-case V3 dataset: 120 development, 30 regression, 30 held-out, 15 failure anchors, 5 win anchors.
  • Gemini semantic judge plus deterministic checks.
  • V12, manual V13, precision V14 and GEPA candidate comparisons.
  • Real GEPA optimize_anything execution with lineage and candidate tree.
  • Output-extractor experiment and hospital domain-pack smoke test.

Not complete

Evidence required for the claim

  • No validated multi-turn candidate conversations.
  • No candidate audio, turn-taking or latency comparison.
  • No real tool state or side-effect verifier.
  • No repeated-run reliability measurement.
  • No owner-reviewed reference labels.
  • No one-time held-out or matched Indus canary run.

Major evaluator weakness

Judge agreement with provisional labels is 100% for primary success and hard safety, 85% for integrity, and 80% for task success—but only 25% for failure category, 25% for component owner, and 35% for locating the first breaking turn within one turn. The system can score broad outcomes better than it can explain why they failed.

Major release-gate weakness

The gate compares aggregate counts. It can approve a candidate that reduces total violations while creating a new severe failure on a different case. It also does not enforce terminal-state accuracy. The “14/15 failure anchors repaired” field really means “candidate passed 14/15”; V12 already passed 11.

The four known candidate regressions
  1. COND-12: converted a conditional future date into a false commitment.
  2. FACT-04: Punjabi response was judged as a task failure.
  3. TREF-06: invented an unsupported website payment route—an integrity regression.
  4. TRST-23: repeated an unnecessary trust/confirmation step.

02 · Research synthesis

EVA is the closest overall reference. VAmoS fills its most important gap.

The right move is not to copy every benchmark. It is to adopt the minimum set of ideas that upgrades the credibility of this EMI demonstration.

Primary reference

EVA-Bench · ServiceNow

Adopt: validated bot-to-bot simulation, separate EVA-A accuracy and EVA-X experience views, repeated trials with pass@1/pass@k/passk, perturbation matrices and per-record artifacts.

Do not copy blindly: the open-source runner expects its own assistant pipeline and several provider credentials. Sarvam Indus is a hosted target; a direct plug-in is not guaranteed.

Paper ↗ MIT repository ↗

Voice realism

τ-Voice

Adopt: clean versus realistic conditions; accents, noise, telephony degradation, interruptions and backchannels; separate task completion from responsiveness, latency, interrupt rate and selectivity.

Defer: its 200 ms tick-based full-duplex orchestrator. It is research-grade infrastructure and not necessary for the first presentation-quality Indus evaluation.

Paper ↗

Execution ground truth

VAmoS Bench

Adopt now: a fresh seeded backend for every scenario, real tool execution, complete tool traces, and assertions that jointly inspect what the agent said and what the tools actually did.

Simplify: use isolated SQLite fixtures for the MVP instead of 100 PostgreSQL containers. Preserve the isolation and assertion invariants.

Paper ↗

Existing optimizer

GEPA

Keep: reflective prompt search with rich evaluator feedback and lineage.

Upgrade: optimize against multi-turn and executable rewards, run multiple seeds, search more than four proposals, and separate opening-message, policy and extractor artifacts.

Optimize Anything ↗

Bot-to-bot is important—but only when validated

Yes. It is the scalable way to measure dynamic multi-turn and voice behavior repeatedly. It is not a replacement for the 20 real calls or the final matched Indus canary. EVA’s key quality-control idea is to reject simulations where the caller bot deviated, ended incorrectly, omitted required information or corrupted the experiment. Unvalidated bot-to-bot data can create a very polished but false benchmark.

Reject

Clone all of EVA and force Indus into it

High integration risk. EVA’s default target pipeline is not Sarvam Indus, and its complete metric stack expects credentials that are not currently available. This can consume time without producing valid evidence.

Recommended

Build an EVA-compatible evaluation layer

Adopt its run structure, simulator validation, Accuracy/Experience metric split, repeated-trial statistics and perturbation schema. Reuse open-source metric code only where provider and trace interfaces fit cleanly.

Later

Add a real Sarvam transport adapter

After the local multi-turn and audio metric layers work, investigate Indus website/SDK or telephony adapters for automated bot-to-bot calls. Until then, use matched human calls for the real hosted-agent evidence.

04 · Evaluation contract

Do not collapse voice quality into one attractive number.

Use two product scores, hard guardrails, diagnostics and reliability. The main business metric remains explicit pay-now commitment among answered eligible calls—not connection rate and not actual payment.

EVA-A inspired

Accuracy / task truth

  • Stateful task completion: the expected PTP/callback/dispute state exists.
  • Faithfulness: spoken dates, amounts, channels and status match variables and tool results.
  • Outcome correctness: extracted disposition matches the actual conversation.
  • Key-entity speech fidelity: amount, due date, TV/product and official app are spoken correctly.
EVA-X inspired

Experience / conversation truth

  • Progression: every agent turn moves toward pay-now or an accurate terminal state.
  • Conciseness: short opening; no full TV specification; no repetitive confirmation.
  • Turn taking: no talking over the caller; correctly yields and resumes.
  • Latency: time to first audio, end-of-turn response delay and dead air.

Realistic effort

A defensible presentation-grade MVP is roughly two to four focused days of code and experiments plus the manual matched calls. A fuller automated Indus bot-to-bot adapter can take longer because the hosted product transport—not model intelligence—is the integration risk.

06 · GEPA v4 experiment

Use GEPA after the reward becomes trustworthy.

The current run proves integration, not search saturation: 24 training cases, 12 validation cases, four proposal attempts and three candidates are too small for the final claim.

Artifact A

Opening message

Optimize identity, lender, Samsung TV context and immediate official-app objective under a strict spoken-length budget. Evaluate first-turn abandonment risk and entity pronunciation.

Artifact B

Conversation policy

Optimize terminal-state handling, conditional commitments, trust resolution, refusals, language switching and tool decisions across full multi-turn trajectories.

Artifact C

Output extractor

Optimize disposition, PTP date, callback and escalation extraction independently. Do not let better output labels disguise worse agent behavior.

Design choiceCurrentGEPA v4Why
Search seeds13 independent seedsShows optimizer stability rather than one lucky path.
Proposal budget412 per seedEnough search to compare meaningful candidate families without uncontrolled expense.
Training signalSingle next responseMulti-turn outcome + tool state + rich feedbackOptimizes the actual workflow.
Dataset use24 train / 12 val60 stratified train / 30 val / 30 shadow devUses current development data while preserving regression and held-out sets.
ArtifactsSystem promptOpening, policy, extractorPrevents one giant prompt from absorbing every failure.
SelectionComposite + aggregate gatesPareto shortlist + per-case hard gatesTask lift cannot trade away integrity or experience.

Never optimize the judge and the agent on the same outcomes in the same cycle. Evaluator prompts can be improved only against a separately human-reviewed calibration set. Otherwise GEPA can learn the evaluator’s blind spots and produce score inflation.

Randomize call order within each arm. Use exact caller-card instructions and record any caller deviations. Calls with simulator/human-protocol violations are invalidated before agent scoring, not counted as agent failures.

What “self-improvement” means after this upgrade

New traces are scored and clustered; the system identifies the first breaking event; routes the failure to the responsible component; generates a bounded repair; evaluates it on multi-turn, execution and voice evidence; and promotes only candidates that pass regression, held-out and canary gates. GEPA automates one branch—the prompt branch—not the entire framework.

08 · Release decision

The release gate is the product.

A credible self-improving system must be able to say “no improvement,” hold a candidate and explain the exact failing case.

Hard stop

Safety and integrity

Zero new hard-safety, false commitment, invented route, unauthorized tool action or spoken/tool-state mismatch. Aggregate improvement cannot offset one new severe case.

Required lift

Task and reliability

Positive paired task delta, no terminal-state regression, improved failure anchors, all win anchors preserved, and pass3 not worse.

Evidence gate

Held-out and voice

One sealed held-out run after method freeze, followed by matched Indus voice calls. Final verdict is promote, hold or rollback.

09 · Interview-ready output

Show the learning system, not a before/after prompt.

Two-minute live narrative

  1. Problem: voice agents fail in conversation, execution and audio—not only in prompts.
  2. Evidence: open one real V12 call and point to its exact first breaking turn.
  3. System: show the failure routed to prompt, extractor, tool or runtime.
  4. Experiment: compare V12 and candidates with task, experience, reliability and tool-state evidence.
  5. Decision: show the gate accepting, holding or rolling back the candidate.

Dashboard additions

  • Run comparator with V12, manual and GEPA candidates.
  • Trace timeline: audio turn, transcript, tool event and failure marker.
  • Accuracy versus Experience quadrant.
  • pass@1 / pass@3 / pass3 reliability gap.
  • Perturbation heatmap by language, noise and behavior.
  • Release checklist with explicit failing cases.
  • GEPA candidate tree and retained negative experiments.

Final claim boundary

Safe now: “I built a governed, domain-configurable improvement framework and found a +5.29pp offline candidate signal that has not passed voice release.” Safe after completion: “The candidate passed our fixed held-out and matched voice protocol with no new severe regressions.” Never claim without payments data: “It increased collections.”
