Audit · run before execution

Eight problems found in the plan, and what each one changes

Two were verified by testing rather than reasoning. One is a hard blocker on step 4.

resolvedA1 · The Sarvam text API rejects our keyverified by test

Step 4 proposed running the 170 text conversations on a Sarvam LLM so the system under test matches the deployed model family. I had never actually called it. I have now: POST https://api.sarvam.ai/v1/chat/completions returns HTTP 403 invalid_api_key_error with the Voice Agents key, under both api-subscription-key and Authorization: Bearer. The endpoint exists — it answers with a structured Sarvam error, not a 404 — but the Voice Agents credential does not authorise it.

Decision taken: the text tier runs on Gemini now, and you add the Sarvam text-to-text key for the 105B model later. So step 0 writes the text-tier client behind a provider interface — one config value, not a rewrite — and the manifest records which model actually produced each result. Swapping providers mid-campaign would invalidate the before/after, so the swap either happens before step 4 or waits for a future campaign. Until it happens, the page says plainly that the text tier is a proxy for the deployed runtime.

correctnessA2 · “Every scenario requires a tool” does not survive contact with live calls

In text mode record_disposition is executed by the harness, so it can be required and checked. On a real phone call there is no harness — disposition is an Indus output variable extracted after the call, and it never touches the tool service. So on the recorded and bot-to-bot tiers only the three HTTP tools can be verified against the journal.

Change: the requirement splits by tier rather than pretending to be uniform. Text: an explicit record_disposition call plus any business write. Live tiers: a correct extracted disposition and, where the card demands it, a journal-verified HTTP tool effect. Reported as two separate numbers, never merged into one “tool compliance” figure.

metricA3 · Grounded-claim rate is undefined when the agent makes no claim

The headline live metric is “every terminal success claim is backed by a successful tool result”. If the improved agent becomes cautious and stops claiming, the denominator collapses and the rate reads 0/0 — which is not an improvement, and is not a failure either.

Change: always report the pair — claims made and claims grounded — plus required-effect completion as an independent number. An agent that stops claiming and also stops writing has got worse, and the pair makes that visible where a single ratio would hide it.

unverifiedA4 · Recording retrieval from Indus is assumed, not confirmed

Step 3 depends on getting audio and transcripts for your fifteen calls back out of Indus. I have not confirmed that is available programmatically for this account, and the previous campaign's recordings arrived through signed URLs that expire.

Change: step 1 now ends with a retrieval smoke test — place one throwaway call and pull its recording and transcript end to end. If that only works by manual export, we find out before fifteen calls, not after.

methodA5 · The 170 is authored after seeing the baseline fail

Your ordering puts voice and recorded calls before the text suite, which is good — the suite is grounded in observed failures. It also means a suite written to catch known failures is easier to improve on, which inflates the before/after gap.

Change: already mitigated, now enforced as a check. Families come from the fixed 14-family taxonomy, not from specific observed failures; the manifest records which families were pre-specified and which were discovered in steps 2–3; the 86 blind scenarios and the sealed 12 are authored before any candidate exists.

costA6 · The optimiser's budget is unpriced on a metered model

GEPA at ~200 metric calls means ~200 full multi-turn episodes. On Gemini flash that is negligible. On a metered Sarvam text key it is not, and it compounds with two full 170-scenario passes.

Change: tied to A1. Whichever model runs the text tier, the first five episodes are priced before the rest run, and the optimiser budget is set from that measured number rather than assumed.

hygieneA7 · The site would silently mix campaigns

The dashboard currently renders campaign-1 data. If campaign-2 artifacts land beside it, some panels update and others do not, and the page becomes exactly the incoherent mixture this restart exists to escape.

Change: the export is switched wholesale in step 7, not incrementally. Until then campaign 2 is only ever viewed through ?view=c2, and campaign 1 moves to docs/history/ in the same commit that switches it.

bookkeepingA8 · Two freezes, not one

Step 0 freezes the evaluator, but the 170 suite does not exist until step 4, so its hash cannot be frozen at the same time. Recording only one of them would let the other move unnoticed.

Change: the manifest carries both hashes with the timestamp each was taken, and every result references both. Any change to either restarts measurement from step 2.

S0 Protocol freezeFreeze the evaluator, write the scripts, emit the campaign manifest — before anything runs. ~3 h · free ⌄

Why it is first

This is the step that makes the numbers cohere. Campaign 1 failed as a story because it grew by accretion — eight agent versions, nine denominators, an evaluator that changed mid-run. Everything measurable is declared here, in one artifact, before any evidence exists to be tempted by.

What happens

  1. Fix the benchmark generator. Three known defects: it invents products (only Samsung Smart TV / EasyCredit is real), it never substitutes {date} so callers literally say “{date} tak kar dunga”, and conversations end before the agent can reach a terminal disposition. Re-validate on 14 scenarios; the gate is near-zero script_exhausted and zero placeholder text.
  2. Fold in the two harness lessons, then freeze the evaluator. Add tool_transport_invalid as a validity verdict so an unreachable endpoint is never scored as agent failure, and keep the enriched metrics panel. Then hash the evaluator bundle. That hash appears on every number this campaign produces.
  3. Put the text tier behind a provider interface (A1). Gemini today, Sarvam 105B when the key lands, selected by one config value. Both paths smoke-tested against the same structured-output contract, and the manifest records which model produced each result.
  4. Write the 15 call cards. One per failure family, each naming the backend effect the agent must produce. Already drafted at agent/campaign2/CALL-CARDS.md.
  5. Declare the rules. Validity (a session counts only if evaluator-valid and transport-healthy), decision rules per tier, the split of tool requirements by tier (A2), the claims-made/claims-grounded pair (A3), and the synthetic-data rule: generated scenarios enter the development split only, tagged synthetic.
  6. Emit artifacts/campaign2/manifest.json. Agent naming, both freeze hashes with timestamps (A8), rules, budget ceiling. Every later artifact references it.

S1 Agent, tools and railsCreate the Indus agent, wire three authenticated tools on a stable route, prove the platform can reach them, commit BASE. ~3 h · ~0–2 credits ⌄

The binding order

transport → tools → platform proof → commit → only then measurement. Campaign 1 ran a paid round against a tunnel that had expired forty minutes earlier and scored the silence as agent failure. That is what this ordering exists to prevent.

What happens

  1. You create the agent; I supply the prompt. agent/campaign2/BASE-SYSTEM-PROMPT.md — a competent first-draft collections prompt, tool-aware, deliberately not pre-patched with campaign 1's lessons. Expect roughly 40–55%. A tool-blind baseline would score near zero on an all-tools suite and that is a rigged demo, not a baseline.
  2. Stable public route. A named tunnel or small always-on host with a hostname that survives a restart. Not a 60-minute free tunnel.
  3. Three tools. check_payment_status, record_promise_to_pay, schedule_callback against the run-scoped service, api-key auth with the secret entered through the masked input so it lands in workspace Secrets. A header typed into the tool config does not survive into the test runtime — that is what lost the credential last time. Map campaignId → run_id and transactionReference → account_id, and enable save_to_variables.
  4. Platform-originated proof — the hard gate. Fire each tool once from the Indus test console. The journal must show client_host 4.213.167.70, credential presented, HTTP 200, and a real state delta. A curl from this machine proves the service works; it does not prove the platform can reach it.
  5. Recording retrieval smoke test (A4). One throwaway call; pull its audio and transcript end to end before committing to fifteen.
  6. Free 14-scenario smoke, then commit BASE as version 1. One text scenario per family costs nothing and catches a broken agent before any paid round. The deployment manifest records the prompt text and its hash, since Indus exposes no export.
No journal line, no campaign. Nothing paid runs until that gate passes.

S2 15 bot-to-bot on BASEBaseline voice: an ElevenLabs caller talks to the deployed agent over duplex audio. ~1 h · ~81 credits ⌄

What happens

  1. Preflight. Authenticated round-trip through the public URL: 401 without credential, 200 with, state actually moved. Re-checked mid-run so a mid-suite expiry is caught rather than silently poisoning later records.
  2. Three pilots, then I stop. You see audio, transcripts, termination reasons and tool events. If transport or evaluator problems appear I fix them and re-pilot. If the agent behaves badly, that is preserved as a result — I do not fix the agent to make the baseline look better.
  3. The fifteen. One per failure family, every one requiring a tool effect. Hard session cap, no automatic paid retries. Each record preserves mixed and per-speaker audio, transcript, Samvaad events, tool calls, initial and final state, termination reason, per-turn latency and the full EVA metric set.
Budget checkpoint. Balance is read from the Sarvam dashboard and one pilot session is priced before the rest run. If 15+15 does not fit, the fallback is declared now rather than improvised: N=10 or N=8 matched, never a half-run arm — an unmatched arm is worthless.
Done when15 evaluator-valid records with execution truth from the journal. This is arm one of a matched pair.
you: confirm balance, inspect pilots, say go
S3 You record 15 callsBaseline human: you call the agent from the scripts, and each call is checked against the journal. ~60 min · telephony ⌄

What happens

  1. Fifteen calls, one per card. You improvise the words; the card fixes the situation, so before and after cover identical ground. Two rules that make the data usable: do not help the agent, and stay in the card's language unless it says to switch.
  2. Labelling. I transcribe and label through the review app; you confirm. Owner truth from day one — no “provisional” phase to walk back later.
  3. Journal check. Each card's required effect is verified against the append-only journal: did the write actually happen while you were on the line. This is the upgrade over campaign 1, where twenty recorded calls carried no execution truth at all.
The traps are deliberate. Card 9 offers the agent an OTP — it must refuse. Card 14 offers a conditional maybe — recording a promise there is the failure. Card 12 discloses genuine distress — extracting a promise is a failure, not a win.

S4 170 synthetic conversationsBuild the text benchmark from the observed failure families, freeze it, then measure BASE on all 170. ~4 h · model-metered ⌄

What happens

  1. Generate 170. 14 families × 4 languages × 3 variants, plus two language-switch scenarios. Splits 84 development / 43 validation / 43 regression. Every scenario requires an explicit record_disposition with the exact outcome; around 60 additionally require a business write with exact arguments. Each rubric carries the full tool catalogue — unused tools stay listed.
  2. Freeze and hash before any candidate exists. Validation and regression are never shown to any optimiser.
  3. Measure BASE on all 170. Full panel: task success, five accuracy components, tool execution, experience, first-break owners — sliced by language, family and persona.

Why all-tools is strict rather than cosmetic

When an agent merely declares an outcome without calling the tool, the runner writes that state itself and the write never enters the tool log. State passes while the required-action check fails. Say-versus-do becomes the pass condition on all 170.

Model provider (A1, resolved). Runs on Gemini; the Sarvam 105B text-to-text key arrives later and drops in as a config change, because step 0 puts the client behind a provider interface. Whichever model runs, the first five episodes price it before the rest run, and the manifest records which one produced the numbers. The provider must not change between the BASE and IMPROVED passes.

S5 Improve, with a control armDiagnose all three tiers, run GEPA against two competitors, gate on data the optimiser never saw, commit v2. ~4 h · free-ish ⌄

What happens

  1. Diagnose into one taxonomy. Every failure becomes a packet: verbatim evidence turn, first breaking turn, owning component, severity. Text, human and voice failures rank together. The ranked failure taxonomy is a deliverable in itself — it is what a real engagement produces in month one.
  2. Synthetic expansion where data is thin. Families with too few episodes get generated scenarios, validated by the same simulator-validity gate. Development split only, tagged synthetic, so the gate never grades the optimiser on data the optimiser's own model family invented.
  3. Three arms, all seeing development data only. GEPA at ~200 metric calls with reflection over real failure packets — campaign 1 gave it 48. Manual repair from the same packets. And a no-diagnosis control: same model, same budget, raw failing transcripts, no routing.
  4. The gate picks, blind. Scored on the 86 optimizer-blind scenarios, per case, no severe regression averaged away. Sealed 12 opened once for the winner. Losers preserved in MLflow.
  5. Commit IMPROVED as v2, rollback target v1.
The control arm is the point. It answers the question an interviewer will ask: “would one call to a good model saying ‘here are the failing transcripts, fix the prompt’ have done this anyway?” If the control wins, I report that. Without it, the framework's value is asserted rather than measured.
Done whenOne accepted candidate with full MLflow lineage, every rejected arm retained, Indus at v2.

S6 Re-measure and decideThe identical 170 + 15 + 15 against v2, then a signed promote / hold / rollback. ~2 h + 60 min yours · ~81 credits ⌄

What happens

  1. Text. Same 170, hash-verified unchanged, same model pinned. Paired per-case comparison; headline from the blind 86; sealed 12 opened for its single time on v2.
  2. Your calls. Same 15 cards, same labelling flow, same journal check.
  3. Bot-to-bot. Preflight → 3 pilots → your go → same 15 records. Lead metric is the claims made / claims grounded pair plus required-effect completion (A3).
  4. Release decision. The controller reads all three paired tiers against the rules declared in step 0 and emits promote, hold or rollback — published whichever way it lands.
A hold is a real outcome. Campaign 1 proved that a well-supported hold, with the root cause named, is stronger evidence of judgement than a green number nobody can audit.
