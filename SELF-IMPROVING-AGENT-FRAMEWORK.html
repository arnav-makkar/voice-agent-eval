Framework first · EMI is one adapter

A governed learning system for any conversational agent.

The framework observes real interactions, establishes reference truth, turns failures into versioned tests, routes each failure to the correct system owner, generates bounded repairs, blocks unsafe regressions, and releases only through human-controlled evidence gates.

Core design decision The framework does not promise that every cycle improves the agent. It guarantees that every cycle produces an auditable decision: promote a verified improvement, hold an inconclusive candidate, or reject a regression and preserve the failure as a permanent test.
Domain-neutralTask, policy, tool, metric and channel packs are replaceable.
Optimizer-neutralGEPA is one plugin beside manual and non-prompt repairs.
Evidence-gatedNo model can change evaluation rules or deploy itself.
ReversibleEvery version has lineage, a decision record and rollback target.

02 · Framework definition

What “self-improving” means here.

A self-improving agent framework is a controlled learning and release system—not an agent that edits its own prompt in production.

It observes

Captures versioned traces and verified downstream outcomes rather than relying only on transcripts or model self-evaluation.

It learns

Converts reviewed failures into reusable tests, clusters and candidate-repair evidence.

It remains governed

Separates candidate generation from evaluation, freezes policies and requires human release authority.

Framework cycle output = { observed evidence, reference annotations, versioned evaluation dataset, diagnosed failure owners, candidate changes, gate results, release decision, rollback target } Success of the framework ≠ “candidate always wins” Success of the framework = “decision is evidence-based, reproducible, safe and reversible”
Allowed automation

Sampling, test generation, simulation, semantic scoring, failure clustering, candidate proposal, experiment execution, reporting and monitoring.

Never delegated to the optimizer

Policy changes, success definitions, evaluation code, held-out expectations, privacy rules, deployment approval or rollback authority.

How each case is created and admitted

1. Seed

Choose one reviewed V12 failure and freeze the trace immediately before its first breaking agent turn.

2. Generate

Gemini 3.6 Flash returns schema-constrained variants; one meaningful factor changes per row.

3. Validate

Python checks ledger arithmetic, enum values, state reachability, hidden-state isolation, deduplication and split leakage.

4. Review + freeze

Regression and held-out rows receive review; datasets are content-hashed, versioned in MLflow and held-out access is sealed.

Frozen EMI promotion gates

Dataset gate

100% seed lineage; valid states; no hidden-state leakage; no duplicates across splits; every critical real failure anchored.

Evaluator gate

≥85% agreement with reviewed annotations and zero missed P0 cases before bulk scoring.

Offline candidate gate

Target-family lift, zero P0, no critical regression, correct account truth and no slower median payment CTA.

Final voice gate

Matched calls show more paired wins than losses—or preserved TSR with materially lower integrity/repetition defects—and no new P0.

Counts are case-study configuration.

The framework accepts coverage policies rather than hard-coded numbers. EMI uses 120/30/30 because six observed families need enough controlled variation for candidate search and transfer testing. Another domain may require different counts.

Multi-objective scorecard

  • Primary verified task outcome
  • Hard safety and compliance
  • Factual and side-effect integrity
  • Turns, latency and cost
  • Handoff and terminal-state quality
  • Channel-specific quality
  • Performance by language, intent and risk cohort
No universal scalar reward.

The framework uses hard constraints plus a metric vector. A candidate cannot trade a safety violation for a higher average task score.

GEPA's exact role

It may generate prompt candidates from development feedback. It does not build the data, define the objective, score exact outcomes, fix tools, change policy, open held-out data, deploy a version or decide success.

07 · Release and operating model

The framework is valuable even when no candidate wins.

Lift

Candidate improves

Promote only after hard gates, transfer evidence, human diff and bounded rollout.

Flat

No meaningful change

Hold control, report power/coverage limits and select the next failure cluster.

Regression

Candidate gets worse

Reject it, preserve the failing trace and prove the release controls worked.

Inconclusive

Evidence is weak

Do not claim improvement; gather targeted cases or improve evaluator reliability.

11 · How to defend the project

The framework is the product. EMI is the proof fixture.

Defensible claim

“I built a domain-configurable framework that turns real conversational failures into versioned tests, routes them to the correct repair layer, compares bounded candidates, blocks unsafe regressions and produces an auditable release decision. EMI recovery is its first end-to-end adapter.”

Claim to avoid

“I generated transcripts, ran GEPA and got a higher TSR, therefore the voice agent self-improved.” That describes a prompt experiment, not a reusable learning system.

Result-independent interview position If the candidate wins, the framework identifies and validates a safe improvement. If it loses, the framework prevents a bad release and explains why. If results are inconclusive, it exposes the evidence gap. All three outcomes demonstrate product judgment, measurement discipline and responsible automation.

Product competency

Defines success, guardrails, ownership, workflow, release policy and operating cadence.

Technical depth

Uses trace schemas, stateful task contracts, evaluators, simulations, optimization, experiment lineage and adapters.

Executive clarity

Separates business outcome, model quality, risk, cost and evidence strength; never hides a negative result.
