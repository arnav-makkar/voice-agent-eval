How it improved

Nobody wrote the fix

The agent's instructions are a long document. Improving it means rewriting that document. Every word of the rewrite came out of an automated search, tested against a real live agent, and gated on cases the search was never allowed to see.

Plainly: the system reads its own failures, proposes a reworded instruction manual, tries it on live conversations, keeps it only if it wins on unseen cases without breaking anything, and ships it. Then it starts again with the winner as the new baseline.

The five stages

Notice

A detector reads every conversation and flags each promise the agent made aloud with no matching record.

Finds the gap between talk and action

Group

Those violations cluster into recurring patterns, and each pattern becomes a test case that can be replayed on demand.

Turns a symptom into something testable

Search

An optimiser proposes a rewritten instruction manual, runs it on live conversations, reads the full record of what went wrong, and reasons about why before its next attempt.

This is the part that writes the fix

Gate

A candidate must beat the old version on situations held back from the search, must not regress a single safety case, and must clear the measured noise floor.

Most candidates die here

Ship

The winner is deployed to the live agent with its exact fingerprint recorded. Rolling back means restoring the previous fingerprint.

Then the winner becomes the new baseline and it all runs again

What the search is actually optimising

It is scored by the same grader the benchmark uses. There is no proxy metric to game: the thing being maximised is the thing being measured.

Instructions

The rules: what to do when, which action to take, how to close a call.

Worked examples

Real conversations that went perfectly, mined from the agent's own history and used to demonstrate the behaviour.

Those two pieces evolve separately. Splitting them was worth doing, and the evidence is measurable:

Original agentno changes 33/60
Rules onlyinstructions rewritten 49/60
Rules and examplesboth pieces 59/60

The worked examples are responsible for 38% of the total gain. Without them the result stops well short.

What stops a bad change from shipping

The gateWhat it demandsOutcome
Unseen cases 60 situations the search is never shown, checked once per round 33 → 57 → 59
Safety veto Any regression on fraud, distress, privacy or credentials kills the candidate outright 40 → 62 → 63
Won more than it lost A statistical test on which individual cases flipped, in both directions +62 fixed, 0 broken
Bigger than the wobble Changes smaller than normal run-to-run variation are reported as noise, not progress observed 26 vs 1.6 floor
The technical names, for the reader who wants them

The search stage is GEPA, a reflective prompt optimiser, run against the deployed agent rather than a simulation. Candidates are selected on a Pareto front, so one survives by being best at something rather than average at everything. A large reasoning model reads full evaluation traces and writes the rationale for each mutation.

The two-part candidate design comes from MIPROv2, where instructions and demonstrations are optimised as separate but jointly selected components.

The "won more than it lost" gate is McNemar's exact test on paired outcomes. The final result had a p value indistinguishable from zero.

The second round is honest about itself. It improved things and broke nothing, but the gain is small enough that it could be chance. Two rounds show the loop can run repeatedly. They do not prove improvement compounds forever, and this site does not claim it.

The one human edit, declared

After the campaign finished, one line was added by hand: the closing rule now names the platform function that actually hangs up the call. Hanging up was never something the search was scored on, so this changes no result on this site. It is flagged wherever it is relevant rather than folded quietly into the numbers.
