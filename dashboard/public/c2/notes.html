Limits

What this does not prove

Strong numbers stay believable only when their boundaries come from the person presenting them. These are the boundaries.

The voice tests are small

Fifteen phone calls and five voice conversations carry no statistics. They show the gains reach real speech. The statistics live in the 180 typed conversations.

One fix has a second explanation

The dispute call was conducted in English on the old agent, because the caller switched language and the agent followed. The new run was in Hinglish. That fix is real in the log but not isolated from the language change.

Duplicate records moved, not gone

On the phone tier this is 14 of 15 both before and after. A triple write disappeared from one call and a double write appeared on another.

Two rounds is not "forever"

The second round improved things and broke nothing, but it is small enough to be chance. The loop demonstrably runs more than once. It has not been shown to keep paying off indefinitely.

Rewording costs a little

With every customer line rewritten, about 82% of the advantage survives. The remaining 18% is sensitive to how things are phrased.

Persuasion was never the goal

The agent accepts a first refusal because its instructions teach exactly that. Collection rate was not optimised and is not claimed. It is the named next objective.

Things found in the platform along the way

An evaluation this close to a live system finds things that are not the agent's fault. They are worth reporting.

The "are you still there" prompt is rude in Hindi

After five seconds of silence the runtime speaks its own line. The stock Hindi text uses the intimate, disrespectful form of "you", injected into a call where the agent has been formal and polite throughout. It is generated from an English source string and was never checked for register.

It was caught only because every transcript gets read rather than sampled.

Two channels handle per-call settings differently

Phone and live voice channels accept settings passed with each individual call. The typed chat channel quietly ignores them and uses stored defaults instead. Since one of those settings decides which account a call writes to, this determines how every tier keeps its evidence separate. Getting it wrong would silently mix two calls together.

The runtime serves the draft directly

There is no separate publish step: the live agent runs whatever the draft currently says, and the version number is a revision counter rather than a release pointer. Version control therefore has to live in this project's own fingerprint checks, not in the platform.

Two different models, one instruction manual

Conversation runs on one model; deciding which action to take runs on a smaller, separate one. Every improvement here was achieved by instruction text steering that second, smaller model. Worth knowing before writing rules for this stack.

The path to production

The first step costs nothing. The monitor needs no labels and no test scripts, so it can watch live traffic today as a standing say-versus-do alarm. Every violation it finds becomes a replay case, which is exactly the input the rest of the loop runs on. Adoption starts with observation, not with letting a search touch production.

1. Objection handling

Give the agent a real position to hold, and score how many turns it takes before it gives up. The obvious next objective.

2. The last broken call

Call 5 still says it will note the response and writes nothing. The failure case is already captured and ready to replay.

3. Quality into the objective

The conversation quality judges run today but only report. Wiring them into what the search optimises is designed and calibrated, not yet live.

4. Watch live traffic

The say-versus-do detector needs no labelled data, so it can run on production calls as a permanent alarm rather than only on tests.
