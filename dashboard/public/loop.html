Step three · self-improvement

The fix wrote itself

The framework found the failures, rewrote the agent's instructions against them, and shipped the rewrite once it won on cases it had never seen.

What is being changed. The agent's behaviour lives in one long instruction document. Improving the agent means rewriting that document. The question is who writes it, and how you know the rewrite is genuinely better.

How one round runs

Stage one is the part that travels furthest. The detector reads the log alone, with no transcript, no script and no labels, so the same stage that opened this round can run on live production traffic and open the next one.

What a candidate is

The search is scored by the benchmark grader itself. No proxy metric to game.

What the search optimises, exactly. Accuracy only: whether the right records reach the log. The experience metrics, conciseness and progression, are measured on every conversation and reported next to each call, but deliberately kept out of the objective. One target keeps the search honest; experience optimisation is a scoped next step, not a silent side effect.

Instructions

The rules: what to do when, which action to take, how to close a call.

Worked examples

Real conversations that went perfectly, mined from the agent's own history and used to demonstrate the behaviour.

The two pieces evolve separately, and the split is worth measuring:

The technical names, for the reader who wants them

The search stage is GEPA, a reflective prompt optimiser, run against the deployed agent rather than a simulation. Candidates are selected on a Pareto front, so one survives by being best at something rather than average at everything. A large reasoning model reads full evaluation traces and writes the rationale for each mutation.

The two-part candidate design comes from MIPROv2, where instructions and demonstrations are optimised as separate but jointly selected components.

The "won more than it lost" gate is McNemar's exact test on paired outcomes. The final result had a p value indistinguishable from zero.

Why this works beyond one agent

The claim is not that one agent got better. It is that the loop transfers.

The monitor needs no labels

It runs over the journal alone, checking seven invariants that any correct call must satisfy. No transcript, no script, no ground truth, no model call. It runs on production traffic exactly as it ran on the benchmark, and on the baseline it recovered 28% of all graded failures at precision 1.00.

The grader needs only tools

Grading compares end states of the world. Any agent whose outcomes are tool calls with expected results can be graded this way. Nothing in the instrument knows what an EMI is.

The adapter is thin

Onboarding a new agent means writing its tool list, the end state each situation should produce, and the failure types that matter in its domain. The loop itself is untouched.

What changes at production scale

Sampling instead of exhaustive runs, noise floors measured per cohort, and a human approval gate before any deploy. The gate ladder already assumes all three.

The first production step costs nothing. Run the monitor on live traffic as a standing alarm, and its findings bootstrap the rest of the loop. The design is built for production and validated on one live agent; performance at production scale is argued from that design, not yet measured.
