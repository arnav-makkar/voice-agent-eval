Step three · self-improvement

The agent fixes itself

The framework found the failures, rewrote the agent's instructions against them, and shipped the rewrite once it won on cases it had never seen.

What is being changed. The agent's behaviour lives in one long instruction document. Improving the agent means rewriting that document. The question is who writes it, and how you know the rewrite is genuinely better.

The improvement cycle

One round of improvement, end to end. Five stages:

StageWhat happens
NoticeA detector reads the log and flags calls that contradict themselves, such as an outcome recorded with nothing behind it. It needs no transcript, no script and no labels, so it can also run on live production traffic.
GroupRepeated flags cluster into patterns, and each pattern becomes a test that can be replayed on demand.
SearchAn optimiser writes new instructions for the agent and tests them against those cases.
GateFour checks decide whether the rewrite is genuinely better. All four must pass.
ShipThe winner is deployed with its exact text fingerprinted, so rolling back is one step. It becomes the next baseline, and the cycle runs again.

What a candidate is

The search is scored by the benchmark grader itself, not by a proxy metric.

What the search optimises, exactly. Accuracy only: whether the right records reach the log. The experience metrics, conciseness and progression, are measured on every conversation and reported next to each call, but deliberately kept out of the objective. One target keeps the search honest; experience optimisation is a scoped next step, not a silent side effect. Persuasion is out of scope for the same reason: the agent accepts a first refusal because its instructions teach that, and collection rate was never optimised or claimed.

Instructions

The rules: what to do when, which action to take, how to close a call.

Worked examples

Real conversations that went perfectly, mined from the agent's own history and used to demonstrate the behaviour.

The two pieces evolve separately, and the split is worth measuring:

Original agentno changes 33/60
Rules onlyinstructions rewritten 49/60
Rules and examplesboth pieces 59/60

The worked examples are responsible for 38% of the total gain. Without them the result stops well short.

The search pipeline

The diagram below is the search stage in full, as it actually ran: two rounds, what each changed, and the gates before deployment. In plain terms, top to bottom:

The current instructions go in at the top. The optimiser proposes a rewritten instruction set, runs it on the live agent over a batch of test situations, and scores it from the log, using the same grader as the benchmark. A second model then reads the full record of what went wrong and writes the reasoning for the next rewrite. Candidates survive by being best at something rather than average at everything, so different strengths stay in the pool.

After round one, the framework mined the winning agent's own perfect calls and attached them to the instructions as worked examples. From that point a candidate has two parts, rules plus examples, and round two searched over both. The champion then faces the four gates, and only after passing all of them is it deployed, fingerprinted, as the new baseline.

The gateWhat it demandsOutcome

Won more than it lost A statistical test on which individual cases flipped, in both directions +62 fixed, 0 broken
Larger than run-to-run variance Changes smaller than normal run-to-run variation are reported as noise, not progress observed 26 vs 1.6 floor
Method references

The search stage is GEPA, a reflective prompt optimiser, run against the deployed agent rather than a simulation. Candidates are selected on a Pareto front, so one survives by being best at something rather than average at everything. A large reasoning model reads full evaluation traces and writes the rationale for each mutation.

The two-part candidate design comes from MIPROv2, where instructions and demonstrations are optimised as separate but jointly selected components.

The "won more than it lost" gate is McNemar's exact test on paired outcomes. The final result had a p value indistinguishable from zero.

Why this transfers

Nothing in the loop is specific to this agent, or to collections.

PartWhy it carries over
MonitorReads only the log, with no labels and no scripts. On the baseline it recovered 28% of all graded failures at precision 1.00, and it runs on live traffic exactly as it ran here.
GraderCompares end states of the world. It works for any agent whose outcomes are tool calls with expected results.
AdapterOnboarding a new agent means writing its tool list, the end state each situation should produce, and the failure types that matter in its domain. The loop itself does not change.

Production readiness, stated precisely. The monitor can run on live traffic today with no labelled data, and what it finds is the loop's input. At production scale the design assumes sampling, per-cohort variance floors, and a human approval gate before any deploy. Performance at that scale is argued from the design and validated on one live agent, not yet measured.
